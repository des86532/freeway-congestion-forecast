03 / SYSTEM-OPTIMAL DIVERSION

怎麼決定要不要分流

先用 +30 分預測估算兩條路線的旅行時間，再用 BPR 容量模型找出不會讓替代道路回堵的最大改道比例 p*。

原始碼：diversion.py測試：tests/test_diversion.py
01 / WHY QUOTA

為什麼要「配額」

導航 App 對每個用戶各自推薦最快路線；壅塞時若所有人同時改走同一條替代道路，替代道路會被灌爆，預期的時間節省消失。系統最佳的做法是限制改道比例，挑出使整體車輛總時間最小的 p*。

常數值意義
PENETRATION0.30App 用戶佔車流比例；可改道比例上限
MIN_SAVING_S300兩路線預測 TT 差至少 5 分鐘才考慮推播
MIN_QUOTA_SAVING_S60配額分流後至少省 1 分鐘
COOLDOWN_MIN30推播冷卻期（分鐘）
P_STEP0.05掃描 p 的步長
MIN_SPEED_FOR_TT5計算旅行時間的車速下限（km/h）
02 / TRAVEL TIME

旅行時間與慢／快路線

route_time_s = Σ ( distance_km / max(speed_kmh, 5) ) × 3600 # 任一段缺值 → None slow, fast = 預測 TT 較大者, 較小者 # 相同時 ground 為慢

決策使用的是 30 分鐘後的預測車速 pred["30"]。這是以同一時刻車速估整條路線的簡化，不做時變行進模擬。

03 / BPR & p*

BPR 與最佳比例 p*

bpr(v, c) = 1 + 0.15 × (v / c)^4 # v：入口 5 分鐘流量，c：capacity.json # 慢路線有比例 p 的流量改道到快路線 vs = v_slow × (1 − p) vf = v_fast + p × v_slow ts = tt_slow × bpr(vs, c_slow) / bpr(v_slow, c_slow) tf = tt_fast × bpr(vf, c_fast) / bpr(v_fast, c_fast) 總車輛時間 = vs × ts + vf × tf p* = argmin 總車輛時間, p ∈ {0, 0.05, …, 0.30} # 7 個點；同分取較小 p
  • 配額下的節省 saving_quota_s = ts − tf；替代路線 TT 為 tf。
  • naive 對照：全部訂閱用戶（p = 0.30）都改道，替代路線 TT 為 alt_tt_naive_s。
  • 系統車輛時間節省：改道前總車輛時間 v_slow·tt_slow + v_fast·tt_fast 減去改道後（配額／naive），單位為輛·秒（每 5 分鐘流量）。
容量在哪裡用？容量只出現在 BPR 公式內，不是推播關卡。入口流量缺漏才會擋下推播（missing_volume）。
04 / DECIDE

decide：依序檢查，任一條成立就停止

順序reason條件
1missing_data任一路線預測 TT 無法計算（預測缺值）
2below_saving慢路線 − 快路線的預測 TT < 300 秒
3missing_volume任一入口流量缺漏、NaN 或 ≤ 0
4no_benefit（算完 p* 後）p* == 0 或 saving_quota_s < 60
5cooldown距上次推播 < 30 分鐘
6ok全部通過 → push = True

注意：no_benefit 在 cooldown 之前，所以冷卻期內的時間點，如果本來就沒有效益，原因會記成 no_benefit。decide 的 actual_speeds 參數目前沒有被使用；判斷只依 pred30_speeds、volumes、capacity 與冷卻狀態。

06 / MESSAGES

訊息與分組

  • 改道訊息 format_message：預測 ts+30 分起、慢路線「最差路段」（慢路線上 pred30 最低者）時速將降至 x km/h；建議改走快路線，預估可省 N 分鐘；僅建議 p*/0.30 的訂閱用路人改道。
  • 維持原路線訊息 format_stay_message：只有 p* < 0.30 時才產生。
  • 兩種訊息都附「資料來源：交通部高速公路局「交通資料庫」」。
  • 分組函式 select_for_reroute(user_id, date, share)：sha256("user|date") 前 8 位十六進位 % 1000 < round(share × 1000)；同用戶同一天結果固定。
實作邊界：select_for_reroute 只有測試在呼叫，推播流程沒有使用；live --push 只送 decision.message 給單一 LINE_USER_ID，stay_message 只在儀表板顯示。也就是說，「依 p* 把用戶分成入選／未入選兩組」目前是設計，不是已接通的功能。
